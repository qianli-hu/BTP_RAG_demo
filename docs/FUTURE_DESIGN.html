1. Planned infrastructure next build, M2.4 → 1.6

Qdrant server-side hybrid; the app goes stateless planned — next build (M2.4)

why The HANA trial ended; and the in-app BM25 (DESIGN D2) makes the app stateful (blocks horizontal scaling, complicates update consistency). Qdrant runs dense (HNSW+cosine) + sparse (BM25, IDF modifier) + RRF fusion server-side in one Query API call; the app drops its in-RAM index entirely.

key implementation decisions (already made) pinned image; UUID5 point ids (payload keeps real chunk id); sparse built from raw text first (parity with today), enriched text is a separate A/B (M2.1); the refusal gate reads a batched dense-only query (fused RRF scores are not cosines; Qdrant doesn't expose prefetch scores); Qdrant's built-in BM25 tokenizer first — the custom identifier-preserving tokenizer only if the identifier-heavy parity subset regresses.

gate full eval must match/beat the M1 baseline registry rows before Qdrant becomes default. SQLite stays as the zero-dependency baseline arm (parameterize, don't archive).

Ship-shape path: docker compose → vLLM planned (M2.4 → 1.6)

docker two services (app built from our Dockerfile; qdrant official pinned image) + a volume for the vectors — docker compose up is the whole demo.

vLLM rent a GPU, serve an open model behind vLLM's OpenAI-compatible endpoint, and the swap is two env vars (OPENAI_BASE_URL, ANSWER_MODEL) through the provider adapter — then run the same eval and put API-vs-self-host on one economics chart. The API's true throughput ceiling is the provider's TPM quota (~1 req/s for token-heavy RAG); owning the ceiling is the business case for self-hosting.

2. Serving at scale can it handle many users at once?

One user at a time is trivial; 50 users at once is where services fall over. The whole question — can the service take concurrent load, and how do you make it take more? — is three ideas that stack. This is unbuilt roadmap; the demo is the before/after chart.

(a) Blocking vs async — the root cause

Think of the server as a waiter and each request as a table; calling OpenAI/HANA is waiting for the kitchen.

BLOCKING (today-ish)
The waiter takes one table's order, walks to the kitchen, and stands there waiting for the food — ignoring every other table. Serving 10 tables at once needs 10 waiters; run out → table 11 waits in line → latency explodes under load.
ASYNC
The waiter takes an order, hands it to the kitchen, and immediately serves the next table. When food is ready the kitchen signals and he delivers it. One waiter serves all 10, because the waiting time is spent on others.

Why this is a huge, cheap win for us specifically: our own latency profile shows ~97% of a request is spent waiting on OpenAI + HANA — the CPU is idle the whole time. async (the event loop) reclaims that idle time so one process serves far more concurrent users, no extra hardware. (The eval loop already uses threads for the same reason; async is the version that scales to hundreds of connections with less overhead.)

(b) Connection pool

Every HANA/OpenAI call needs a connection, and opening one is slow (a TLS handshake, tens of ms). A pool keeps a few permanently open and reuses them — borrow one per request, return it when done.

A real bug this fixes in our code: HanaStore opens one connection + one cursor and reuses it. A single shared cursor is not safe when two requests run at once — they corrupt each other's results. The fix is a small pool (one connection per in-flight request). The OpenAI SDK already pools its HTTP connections, so that side is mostly handled.

(c) Load test — measure the ceiling, don't guess it

A load test (locust in Python, k6 in Go) spawns N virtual users hammering /ask and records every response time. Ramp N up (10 → 50 → 100) and watch for where latency spikes or errors start — that's your capacity.

(d) The vocabulary — p50 / p95 / p99 & throughput

termmeaning
p50 (median)half of requests are faster than this
p9595% are faster — i.e. your slow 5%
p99the worst 1% — the user who rage-quits
throughputrequests/second the system completes

Why percentiles, not the average: 100 requests — 99 take 2 s, one takes 30 s. The average is ~2.3 s (looks great) but p99 = 30 s, and that one furious user is exactly who you lose. Tail latency is the real UX killer and the average hides it. async + pool aim to raise throughput (more users, same box) while keeping p99 low under load.

The whole row as a build arc → the demo: (1) write a locust file; (2) run it on the current service → baseline p50/p95/p99 + throughput + where it breaks; (3) convert the hot path to async (AsyncOpenAI, await) + add a HANA pool; (4) re-run the same test; (5) demo = the before/after chart: "throughput X → Y req/s, p99 A → B."

Honest wrinkle: OpenAI ships a native AsyncOpenAI client (that call goes fully async easily), but HANA's driver (hdbcli) is synchronous — a blocking DB call would freeze the event loop — so it runs in a thread pool (run_in_executor). Knowing which dependency is async-native vs needs-a-thread is the detail that shows this was built, not just read about.

3. Evaluated & rejected

RAPTOR — recursive clustering + summary tree rejected 2026-07-18

what it was Cluster chunks (UMAP+GMM), LLM-summarize each cluster, recurse into a tree, index summary nodes alongside leaves — pre-assembling scattered evidence at index time.

why rejected (a) global re-cluster + re-summarize on every corpus update — no clean incremental insert; (b) stochastic clustering fights fingerprint reproducibility; (c) summary nodes break citation semantics (generated text cited as source). Replaced by an all-incremental stack: contextual sparse → reranker + parent/adjacency expansion → doc2context — every technique per-chunk or query-time. Revisit only for large cross-document thematic corpora.

4. Alternative architecture — the LLM Wiki pattern v3 exploration

Karpathy's "LLM Wiki" (April 2026) is the far end of the same spectrum as our FUTURE.md §11 thesis — spend the compute on corpus structure, not the matcher. Compile the corpus into an LLM-maintained wiki once, then answer by reading it: no embeddings, no vector DB.

The three layers

layerwho owns itwhat it is
Raw sourcesyou (immutable)curated documents; the LLM reads them, never edits them
The wikithe LLM (entirely)a directory of cross-referenced markdown pages, fronted by index.md + log.md
The schemayou + the LLM (co-evolved)a config doc (CLAUDE.md/AGENTS.md) telling the agent how the wiki is structured and which workflows to follow — the load-bearing part

The schema documents structural conventions (directory/naming, frontmatter, page types), workflow procedures (how to ingest a source, resolve contradictions, update cross-references, when to lint), and quality standards (every claim links to a raw source; contradiction severity levels; freshness checks). Contradictions are tiered: a hard contradiction stops the ingest run and holds the commit for manual resolution; a soft contradiction is flagged and explained but non-blocking. A single source might touch 10–15 wiki pages — that fan-out is the point: synthesis is done at ingest, not re-derived per query.

How it maps to BTP_RAG

Our chunker already extracts a heading tree (section_path, parent_section_id); the wiki takes that idea to its limit (an LLM writes the structure). For our 3 well-structured SAP docs it's a plausible v3 experiment; the cheaper near-term moves remain doc2query / reasoning over our existing TOC (see FUTURE.md §11).
