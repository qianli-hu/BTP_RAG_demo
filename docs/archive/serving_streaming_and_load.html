SSE streaming & the load/async row — explained

Two things: (1) what streaming is and how you'd test it; (2) row #2 of the serving table, from scratch.

Part 1 — What "SSE streaming" means

A normal HTTP request is one round trip: the client asks, the server computes the entire answer, sends it back in one lump, done. For an LLM that takes 5–17 s, the user stares at a spinner the whole time, then the whole answer appears at once.

SSE = Server-Sent Events. The server replies with Content-Type: text/event-stream and keeps the connection open, pushing a sequence of small text events as they're ready — each one is literally a line data: .... It's a one-way stream (server → client) over one ordinary HTTP connection. (WebSockets are the two-way, heavier cousin; SSE is the simple right tool here.)

An LLM generates one token at a time. OpenAI's API with stream=True hands you those tokens as they're produced. So your endpoint forwards each one the instant it arrives, and the UI appends it — the answer types itself out like ChatGPT.

The one wrinkle for our system (why it's cheap but not literally free): /ask today returns one JSON with answer + citations + judge. But citations are parsed from the complete answer, and the judge needs the whole answer. So the streaming flow sends two kinds of events:

data: {"type":"token","text":"Use "}      <- repeated, live, as tokens arrive
data: {"type":"token","text":"the "}
   ... (many) ...
data: {"type":"done","citations":[...],"cost":0.0012}   <- once, at the end

The prose streams live; citations + judge attach on the final done event. Refusals don't stream at all — the score gate fires before any LLM call, so a refusal is instant.

Part 1b — How you BUILD and TEST it

Build (a few hours)

  1. Add a /ask/stream route that calls OpenAI with stream=True and is a Python generator: for each delta, yield "data: ...".
  2. Wrap it: return StreamingResponse(gen, media_type="text/event-stream").
  3. UI reads the stream and appends each token; on the done event it renders citations + judge.

Test (this is the real question — how do you PROVE it streams?)

testwhat it checkshow
curl -N (eyeball)tokens actually arrive incrementally, not in one lump curl -N localhost:8000/ask/stream -d '...' — the -N disables buffering; you watch words trickle in. If they dump at the end, something is buffering.
TTFT assertionit's genuinely streaming, not faking it measure time-to-first-chunk vs time-to-last; assert first < ~1.5 s while total is 5 s+. If first ≈ total, it's not streaming.
equivalencestreaming didn't change the content collect all token events, reassemble the string, assert it equals the non-streaming /ask answer for the same query.
contractthe structured data still arrives assert the final done event carries citations + cost (so the UI/judge still work).
anti-bufferingno proxy/middleware silently buffers the stream assert the response has no Content-Length and uses chunked transfer — the common bug that defeats streaming.

Part 2 — Row #2 decoded: load test → async → connection pool

Row #2 is really one question: can your service handle many users at once, and how do you make it handle more? One user at a time is trivial. 50 users hitting it simultaneously is where services fall over. Three ideas stack up.

(a) Blocking vs async — the root cause

Think of your server as a waiter, and each request as a table. Calling OpenAI/HANA is "waiting for the kitchen."

BLOCKING (today-ish)
The waiter takes one table's order, walks to the kitchen, and stands there waiting for the food — ignoring every other table. To serve 10 tables at once you need 10 waiters. Run out of waiters → table 11 waits in line → latency explodes under load.
ASYNC
The waiter takes an order, hands it to the kitchen, and immediately serves the next table. When food is ready the kitchen signals and he delivers it. One waiter serves all 10 tables, because the "waiting" time is spent on others.

Why this is a huge, cheap win for us specifically: your own latency chart says 97% of a request is spent waiting on OpenAI + HANA — the CPU is idle the whole time. async (the event loop) reclaims that idle time so one process serves far more concurrent users, no extra hardware. (Your eval loop already uses threads for the same reason — async is just the version that scales to hundreds of connections with less overhead.)

(b) Connection pool

Every HANA/OpenAI call needs a connection, and opening one is slow (a TLS handshake, tens of ms). A pool keeps a few connections permanently open and reuses them — borrow one per request, return it when done — instead of open/close every time.

A real bug this fixes in our code: HanaStore opens one connection + one cursor and reuses it. A single shared cursor is not safe when two requests run at once — they corrupt each other's results. The fix is a small pool (one connection per in-flight request). The OpenAI SDK already pools its HTTP connections, so that side is mostly handled.

(c) The load test — you MEASURE the ceiling, you don't guess it

A load test (tools: locust in Python, k6 in Go) spawns N virtual users hammering /ask and records every response time. You ramp N up (10 → 50 → 100) and watch for the point where latency spikes or errors start — that's "where it breaks," your capacity.

(d) p50 / p95 / p99 and throughput — the vocabulary

termmeaning
p50 (median)half of requests are faster than this
p9595% are faster — i.e. your slow 5%
p99the worst 1% — the user who rage-quits
throughputrequests/second the system completes

Why percentiles, not the average: say 100 requests — 99 take 2 s, one takes 30 s. The average is ~2.3 s (looks great!) but p99 = 30 s — and that one furious user is exactly who you lose. Tail latency (p99) is the real UX killer, and the average hides it. async + pool aim to raise throughput (more users, same box) while keeping p99 low under load.

The whole row as a build arc → your demo

  1. Write a locust file (N users POST /ask).
  2. Run it on the current service → record baseline p50/p95/p99 + throughput + where it breaks.
  3. Convert the hot path to async (AsyncOpenAI, await the calls) + add a HANA pool.
  4. Re-run the same test → record the new numbers.
  5. Demo = the before/after chart: "throughput went X → Y req/s, p99 dropped A → B."
Honest wrinkle worth knowing (good interview detail): OpenAI ships a native AsyncOpenAI client, so that call goes fully async easily. But HANA's driver (hdbcli) is synchronous — a blocking DB call would freeze the event loop — so you run it in a thread pool (run_in_executor) so it doesn't block. Knowing which dependency is async-native vs needs-a-thread is exactly the kind of detail that shows you've actually built this, not just read about it.
