BTP_RAG — Design Decisions & Evidence

Every load-bearing decision: what we chose, why, and the measurement behind it. Sibling doc: design_system.html (the system map). The deeper reviewed plan is docs/BUILD_PLAN.md; run history with fingerprints is eval/registry.jsonl. Updated 2026-07-22.

Retrieval & storage

D1 · Hybrid retrieval: dense ⊕ BM25, fused by RRF shipped

why Dense embeddings catch paraphrase ("how do I make search faster" → HNSW section); sparse BM25 catches exact rare identifiers (REAL_VECTOR, COSINE_SIMILARITY) that embeddings fumble. Reciprocal Rank Fusion combines by rank, so incompatible score scales never need calibrating.

evidence hit@5 0.78 with both routes; the custom tokenizer keeps SQL identifiers intact (tokenize() test-pinned).

D2 · BM25 in the app layer (v1) shipped · superseded by D12 plan

why HANA free tier blocks in-DB full-text indexing (verified empirically — CREATE FULLTEXT INDEX rejected). App-side rank_bm25 rebuilds the index in ~38 ms at startup.

consequence the app is stateful (index in RAM) — acceptable at 1,216 chunks, wrong at scale; fixed by D12 (server-side hybrid), which makes the app stateless and horizontally clonable.

D3 · Two-layer refusal gate shipped

why Retrieval always returns the 5 least-bad chunks — someone must decide "good enough?". Layer 1: top cosine < 0.56 → refuse with zero LLM cost (~0.2 s). Layer 2: the prompt's escape hatch — the model refuses when the context lacks the answer. Layer 1 catches off-topic; layer 2 catches on-topic-but-unanswerable.

evidence threshold calibrated on the 7 negatives (max negative 0.550 < 0.56 < min positive 0.572); negatives 7/7 refused at baseline, 0 false refusals on test. Caveat discovered by measurement: layer 2 is a reasoning task — see D8.

D4 · Citations are chunk-ids, validated by rule shipped

why URL-level citation checks pass wrong-section citations (many PDF chunks share one URL). A cited chunk-id must exist in the corpus and be in that query's retrieved set — hallucinated citations are structurally detectable.

evidence 40/40 citation validity at the M1 baseline; the regex extraction from streamed plain text preserved the same guarantee after D7.

Serving

D5 · SSE streaming; structured data rides the final event shipped

why Perceived latency: the user watches the answer type instead of staring at a spinner. JSON can't stream (unreadable until the last brace), so the model writes plain text with inline citations; citations/latency/cost need the finished text and ride one final done event. Errors travel in-band (the 200 is already sent).

evidence TTFT median 2.1 s vs 4.8 s total on synthesis questions (5-run sequential, committed artifact) — >50% of perceived wait removed.

D6 · Single-run claims are banned policy, enforced by artifacts

the lesson Streaming shipped with a single-run headline ("TTFT 1.36 s, 72% of wait eliminated"). Three repeat runs falsified it: the passing run was a 1-in-6 outlier; the same question was refused 5/6 times at the then-default config. Latency variance on a shared API is huge (TTFT 1.1→12.7 s on identical config).

policy published latency/refusal claims = medians of ≥5 sequential runs; raw per-run artifacts committed under eval/measurements/; tuning-time generation runs 3× on refusal-prone types.

D7 · One canonical generation contract shipped (prompts v3)

the failure it fixes v2 had two public answer protocols: /ask made the model emit a JSON envelope while /ask/stream used plain text — different prompts, different reasoning effort — and the eval measured only the path the demo no longer used. Eval-what-you-serve was silently violated.

the fix The model always writes plain text + inline citations; endpoints assemble JSON; generate()/ask() are 4-line buffered wrappers over the streaming twins. One code path, two transports — the eval covers both by construction. Also split ANSWER_/JUDGE_REASONING_EFFORT so tuning the answerer can never silently change the judge.

D8 · Reasoning effort: low is the operating point shipped (measured)

the finding Layer-2 refusal ("is the answer in this context?") and false-premise correction are reasoning tasks. Cut thinking to minimal and the model takes the refusal escape hatch on anything requiring evidence assembly.

Eval discipline

D9 · Evidence atoms: chunking-independent gold labels shipped

why Gold labels keyed to chunk ids/sections break the moment chunking changes — the experiment would invalidate its own labels. An atom is {doc, verbatim quote}; a chunk covers it iff the normalized quote appears in its text. Labels survive any re-chunking; every atom is machine-verified to exist in the corpus at validation time.

payoff evidence-recall@5 (graded) and complete@5 (strict) — metrics that see partial evidence coverage. Single-evidence hit@k scores a retrieval "perfect" the moment one gold chunk appears, even when the answer needs four. Baseline immediately exposed the M2 target: 9/35 atom-carrying items missing ≥1 evidence piece in top-5 (one answered from partial evidence: correctness 0.65).

D10 · Dev/test split; judge = answering view shipped

dev/test Tuning on the regression set turns it into a training set (external review finding). 22 dev / 18 test + 4/4 on the new questions, stratified per type, assigned at authoring time. Sweeps and thresholds tune on dev; published verdicts come from test only. Baseline honestly shows the gap: dev correctness 0.99 vs test 0.908.

judge invariant The judge's context is built by the SAME function as the answering view (build_judge_context = build_answering_context) — the judge scores exactly what the model saw. Faithfulness vs raw-text-only was considered and rejected: it would mislabel faithful use of provided context as hallucination; bad enrichment is caught by correctness-vs-gold (+ planned source_groundedness) instead.

D11 · Four provenance views over one node shipped (guardrails ahead of cargo)

why M2 adds machine-generated enrichment (doc2context, maybe doc2query). Generated text boosting findability must never be quoted as evidence (citation laundering) or leak into the judge. Retrieval view sees everything; answering view sees authoritative text (+labeled generated only if explicitly promoted — a fingerprinted A/B, off by default); citation view is authoritative-only; judge view is the answering view.

enforcement VIEW_POLICY in config + fingerprint; 6 governance tests make violations a test failure, not a code-review hope.

Rejected & planned

R1 · RAPTOR — evaluated and rejected rejected 2026-07-18

what it was Cluster chunks (UMAP+GMM), LLM-summarize each cluster, recurse into a tree, index summary nodes alongside leaves — pre-assembling scattered evidence at index time.

why rejected (a) global re-cluster + re-summarize on every corpus update — no clean incremental insert; (b) stochastic clustering fights fingerprint reproducibility; (c) summary nodes break citation semantics (generated text cited as source). Replaced by an all-incremental stack: contextual sparse → reranker + parent/adjacency expansion → doc2context — every technique per-chunk or query-time. Revisit only for large cross-document thematic corpora.

D12 · Qdrant server-side hybrid; app goes stateless planned — next build (M2.4)

why HANA trial ended; and D2's in-app BM25 makes the app stateful (blocks horizontal scaling, complicates update consistency). Qdrant runs dense (HNSW+cosine) + sparse (BM25, IDF modifier) + RRF fusion server-side in one Query API call; the app drops its in-RAM index entirely.

key implementation decisions (already made) pinned image; UUID5 point ids (payload keeps real chunk id); sparse built from raw text first (parity with today), enriched text is a separate A/B (M2.1); refusal gate reads a batched dense-only query (fused RRF scores are not cosines; Qdrant doesn't expose prefetch scores); Qdrant's built-in BM25 tokenizer first — custom identifier-preserving tokenizer only if the identifier-heavy parity subset regresses.

gate full eval must match/beat the M1 baseline registry rows before Qdrant becomes default. SQLite stays as the zero-dependency baseline arm (parameterize, don't archive).

D13 · Ship-shape path: docker compose → vLLM planned (M2.4 → 1.6)

docker two services (app built from our Dockerfile; qdrant official pinned image) + a volume for the vectors — docker compose up is the whole demo.

vLLM rent a GPU, serve an open model behind vLLM's OpenAI-compatible endpoint, and the swap is two env vars (OPENAI_BASE_URL, ANSWER_MODEL) through the provider adapter — then run the same eval and put API-vs-self-host on one economics chart. The API's true throughput ceiling is the provider's TPM quota (~1 req/s for token-heavy RAG); owning the ceiling is the business case for self-hosting.

The meta-decision

D0 · Everything is a fingerprinted toggle, judged by the harness

Every capability that changes results (store, prompts version, efforts, view policy, rerank, future RAPTOR-like ideas) is a config toggle recorded in the experiment fingerprint, so: old behavior is always one flag away; every A/B is attributable to an exact configuration; and no improvement is "believed" — it must beat the baseline registry row on the full metric set (quality + refusals + citations + latency + cost), paired per-question, dev for tuning, test for the verdict.
