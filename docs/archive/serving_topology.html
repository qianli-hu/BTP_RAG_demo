BTP_RAG — serving topology

Who calls whom for one /ask. Request flows left → right; the answer streams back ← .

The 6 steps, in words

  1. 1 — You open localhost:8501; your browser talks to the Streamlit process.
  2. 2 — You hit "Ask". Streamlit makes an HTTP POST to localhost:8000/ask — here Streamlit is a client of FastAPI.
  3. 3 — FastAPI's route handler calls core.ask("question") — an ordinary in-process Python function call, not a network hop. Your whole retrieval+generation engine lives inside this one process.
  4. 4 — Inside core.ask, providers calls the OpenAI API (embed + generate) over HTTPS, and the store queries HANA/SQLite. FastAPI is now a client of those.
  5. 5 — The answer + citations flow back to Streamlit as JSON.
  6. 6 — With SSE, step 5 isn't one lump at the end — tokens stream back piece-by-piece and Streamlit types them out live (citations + judge attach once the full text arrives).

Client vs Server vs Host

termmeaningin our stack
CLIENTthe thing that starts a requestBrowser · Streamlit (to the API) · FastAPI (to OpenAI/HANA)
SERVERthe thing that listens & respondsStreamlit (to the browser) · FastAPI (to Streamlit) · OpenAI/HANA
HOSTthe machine a process runs ondev: your MacBook (localhost) · prod: cloud host(s)

Key idea: client/server are roles in a single request, not fixed identities. Streamlit is a server to your browser and a client to the API at the same time. One host can run many servers (here: two processes, ports 8501 and 8000, both on your laptop).

Your specific questions

"Is FastAPI a server?" — FastAPI is the framework (a library) that turns core.ask into an HTTP endpoint. The actual server process is uvicorn — that's why you run uvicorn app.main:app. Colloquially "the FastAPI server" = uvicorn running your FastAPI app.

"…like Swagger?" — Swagger (the page at /docs) is the auto-generated interactive documentation + test console for your endpoints. FastAPI builds it for free. It documents the service; it isn't the service.

"Is Streamlit built on top of FastAPI?" — No. They're two independent web servers. Streamlit serves the UI to your browser and is itself just an HTTP client of FastAPI (requests.post(...) in ui.py). You could delete Streamlit and call /ask with curl, or delete FastAPI and call core.ask() in a Python REPL — each layer is optional.

"Constantly on, or warm-up?" — The uvicorn process runs continuously once started (a loop accepting connections) until you Ctrl+C. There's a one-time warm-up at boot: the lifespan builds Engine() once (loads chunks, builds the BM25 index ~38 ms, warms caches). After that every request is fast — that's exactly why the engine is built at startup, not per request.

"In production, how is it kept always-on?" — You don't run uvicorn by hand. You hand the process to an orchestrator (Cloud Foundry via cf push, or Kubernetes) that: runs N replicas for capacity + redundancy, health-checks them by polling your /health endpoint, auto-restarts crashed ones, and load-balances across them. So yes — it's mostly declarative: you state "keep 3 healthy instances alive" and the platform enforces it. That is literally what /health is for.
