Karpathy's "LLM Wiki" pattern

A retrieval alternative (April 2026): compile the corpus into an LLM-maintained wiki once, then answer questions by reading it — no embeddings, no vector DB. Focus below: the schema/config layer.

The three layers

layerwho owns itwhat it is
Raw sourcesyou (immutable)your curated documents. The LLM reads them, never edits them.
The wikithe LLM (entirely)a directory of markdown pages it creates/updates, with cross-references kept consistent, fronted by index.md + log.md.
The schemayou + the LLM (co-evolved)a config doc (CLAUDE.md / AGENTS.md) telling the agent how the wiki is structured and what workflows to follow.

The schema/config layer — the load-bearing part

Karpathy calls it "the key configuration file — what makes the LLM a disciplined wiki maintainer rather than a generic chatbot." It's plain markdown, human-editable, and you and the agent co-evolve it over time. It documents three kinds of thing:

1. Structural conventions

  • directory organization & file naming
  • frontmatter format (the metadata block atop each page)
  • page types (e.g. entity pages, concept pages, summary pages, analysis pages)

2. Workflow procedures

  • how to ingest a new source (steps below)
  • how to handle contradictions between sources
  • how to update cross-references when pages change
  • when to run a lint pass (consistency check across the wiki)

3. Quality standards

  • citation requirements (every claim links back to a raw source)
  • contradiction severity levels (see below)
  • freshness checks (is a page stale vs newer sources?)

Ingestion workflow (what the schema makes the agent do)

On a new source, the agent:

  1. reads the source and discusses key takeaways with you;
  2. writes a summary page;
  3. updates index.md;
  4. updates relevant entity and concept pages across the wiki;
  5. appends an entry to log.md.

Scale note: "a single source might touch 10–15 wiki pages." That fan-out is the whole point — the synthesis (cross-links, contradictions) is done at ingest, not re-derived per query.

Conflict resolution (tiered severity)

severitybehavior
hard contradictionstops the ingestion run, holds the commit, sends a notification — wait for manual resolution with a documented justification.
soft contradictionflagged, referenced, compared, explained — but non-blocking.

Query workflow — no embeddings

Two special files replace the vector DB:

  • index.md — a catalog of every page: link + one-line summary + optional metadata. The agent reads this first, then drills into the relevant pages. "Works surprisingly well at moderate scale (~100 sources, ~hundreds of pages)."
  • log.md — append-only record of ingests/queries/lint passes, "parseable with simple unix tools."

To answer: read index → open relevant pages → synthesize an answer with citations. And crucially — good answers get filed back into the wiki as new pages, so a question you ask once becomes a compounding asset instead of disappearing into chat history.

Core insight — and how it relates to BTP_RAG

Compile once, query many. Vector RAG re-discovers knowledge from fragments on every question; the wiki accumulates compiled synthesis, so cross-references and contradictions are resolved up front, making later queries faster and more coherent.

It's the far end of the same spectrum as our FUTURE.md §11 thesis — spend the compute on corpus structure, not the matcher. Our chunker already extracts a heading tree (section_path, parent_section_id); the wiki takes that idea to its limit (an LLM writes the structure). For our 3 well-structured SAP docs it's a plausible v3 experiment; the cheaper near-term moves remain doc2query / reasoning-over-our-existing-TOC.
