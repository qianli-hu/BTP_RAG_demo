2. The canonical generation path one kitchen, two transports

There is exactly one generation code path. The model always writes plain text with inline [chunk-id] citations; JSON is assembled by the endpoint, never by the model. Non-streaming functions are 4-line buffered wrappers over their streaming twins — so the eval harness, /ask, and /ask/stream run literally identical logic:

chat_stream()      providers.py   raw tokens from the LLM, one by one (+ usage last)
   ↑ wrapped by
generate_stream()  generate.py    refusal gates · accumulates copy · extracts citations
   ↑ wrapped by                   from the FINISHED text, validated ⊆ retrieved set
ask_stream()       core.py        retrieval first · TTFT stamp · trace · request log
   ↑ wrapped by
/ask/stream        main.py        SSE: data:{token}… then one done-event (citations,
                                  latency, cost — structured parts need finished text)
/ask               main.py        SAME chain, buffered: collect tokens, assemble JSON

generate() = for kind, payload in generate_stream(...): if kind == "done": return payload
ask()      = same wrapper over ask_stream()
Why it's built this way: streaming shipped first as a separate prompt+path and the eval silently kept measuring the old path — a measured eval/serving divergence (the streaming path refused synthesis questions 5/6 while the eval saw nothing). Collapsing to one canonical path made "eval measures what users get" true by construction, not by discipline.

3. The four provenance views views.py · VIEW_POLICY

One stored node is rendered differently for four audiences. The discriminator is always provenance: machine-generated enrichment may aid findability but must never be quoted as evidence. Policy lives in config.VIEW_POLICY and is stamped into every experiment fingerprint; six governance tests enforce it.

viewconsumermay containinvariant
build_retrieval_textsearch index (dense + sparse) everything: raw text, section path, generated context, synthetic queries maximally rich — nobody quotes it
build_answering_contextanswer LLM raw text + real metadata; generated context ONLY if promoted, then labeled [GENERATED — NOT citable evidence] synthetic queries: no code path exists
build_citationthe user's source link raw text + real doc/section/URL only generated text can never appear (no citation laundering)
build_judge_contextgpt-5 judge defined as the answering view — it literally calls it (one builder, two callers) judge scores what the model saw; drift impossible
Fault attribution when generated context is promoted: answer_context_faithfulness (vs what the model saw) + correctness (vs gold) + planned source_groundedness (vs raw evidence) split the blame: groundedness FAIL + faithfulness PASS ⇒ the pipeline shipped a bad enrichment; both FAIL ⇒ the model hallucinated.

5. The eval spine the actual product

piecewhat it does
gold set — 48 items, 8 files = 8 failure modes factual(12) · table(6) · cross-doc(5) · evidence-dense(8, multi-atom) + adversarial: distractor(5) · false-premise(3) · entity-confusion(2) · negative(7, must refuse exactly)
dev/test split (22/18 + 4/4) dev tunes (sweeps, thresholds); test is sealed — final verdicts only. Assigned at authoring time, stratified per type
evidence atoms gold evidence = verbatim quotes from source docs ({doc, quote}), matched by normalized substring containment — labels survive any re-chunking. Every atom machine-verified to exist
evidence-recall@5 / complete@5 fraction / all-of an item's atom set covered in top-5 — measures partial evidence coverage, which single-evidence hit@k structurally cannot see
judge triad faithfulness (vs what the model saw) · correctness (vs gold/truth) · relevance (vs the question) — independent axes; disagreements attribute faults
fingerprint + registry every run stamped with models + params + prompt version + view policy + efforts + gold/corpus hashes; appended to eval/registry.jsonl; per-item results archived immutably under eval/out/runs/
committed measurements eval/measurements/: repeat-probe + sweep scripts with raw per-run artifacts — every published latency/refusal claim is a distribution, never a single run
